# Підводні камені

Короткі записи про те, що наступна сесія інакше відкриє заново. Кожен запис: що сталося, чому, що робити. Нові — знизу свого розділу.

## Розгортання й вузол (SPEC-13a, 2026-11-18)

- **`ufw limit 22/tcp` ламає власні інструменти.** Обмеження пускає ≈6 нових з’єднань за 30 с з однієї адреси, а `infra/ops` відкриває з’єднання SSH на кожен крок і перевірку — підготовка вузла падала з `Connection timed out`. Невдалі спроби теж подовжують блокування. Правило на вузлі — `ufw allow 22/tcp` (вхід лише за ключем, root і паролі вимкнено); міняти правило брандмауера — одним з’єднанням (`allow` перед `delete limit`).
- **Крок, що вимикає вхід root, не можна перевіряти новим з’єднанням root.** Перевірка `sshd -T` іде в тому самому з’єднанні, що й зміна; ззовні підтвердження — вхід `deploy`.
- **`pnpm import …` — вбудована команда pnpm 12.** Скрипт пакета викликати як `pnpm run import catalog [--apply]` (у контейнері сервера: `docker exec <сервер> pnpm run import catalog --apply`).
- **Локальний dev-сервер переписує `server/src/payload-types.ts` з LF.** `git status` показує файл зміненим, `git diff` порожній; запобіжник «чисте дерево» в `deploy` чесно відмовляє. Ліки: `git add server/src/payload-types.ts` (вміст той самий, індекс оновлюється).
- **Перше розгортання середовища не має звідки взяти каталог по https.** Збірка сайту (`test` + `http`) читає `T2F_CATALOG_URL`; Worker’а середовища ще немає. Для першого разу: локальний сервер worktree (`pnpm stack`) і `T2F_CATALOG_URL=http://127.0.0.1:<порт>` (http на loopback дозволено лише в тестовій збірці); після `import catalog --apply` на вузлі наступні розгортання беруть каталог із самого середовища.
- **Нове ім’я в Cloudflare може «не існувати» на машині розробника ще довго** (локальний кеш негативної відповіді DNS). Перевіряти через `curl --resolve <ім’я>:443:<адреса з nslookup <ім’я> 1.1.1.1>`.
- **`next build` Payload потребує змінних середовища вже під час збірки** («Collecting page data» завантажує `payload.config.ts`). В образі це заглушки класу `test` лише в одному `RUN`; до бази збірка не під’єднується.
- **Payload не читає `migrations/index.ts`** під час `payload migrate` — лише файли міграцій у теці.
- **Compose `environment:` перекриває `ENV` образу й `env_file`.** `T2F_ENV`, `T2F_HOST`, `T2F_SERVER_PORT` задає Compose вузла; `T2F_COMMIT` вшито в образ — у файли змінних їх не писати.
- **`wrangler deploy` без термінала мовчки забирає Custom Domain в іншого Worker’а** (`override_existing_origin`). Для основного домену єдині запобіжники — подвійний прапорець і перевірка власника імені (`--take-domain-from`).
- **Тести, що запускають `cf.mjs`, мусять передавати тимчасову `localDir`.** Інакше вони читають справжню `infra/cloudflare/.local` (позначка Access, токен тунелю) і поводяться по-різному на різних машинах.
- **`scripts/check-secrets.mjs` дивиться лише відстежувані файли.** Для нових файлів — спершу `git add -N`. Тестовий пароль чи ключ потребує `// check-secrets: allow <причина>` у тому ж рядку (порожня позначка не рахується).
- **Вимкнений вузол DigitalOcean тарифікується;** зміна розміру лише CPU/RAM зворотна (диск не росте), потребує вимкнення: ≈110 с простою на вузлі з 9 ГБ зайнятого диска.
- **Завантаження статики Worker’а інколи обривається** («Asset upload failed. Retrying…» до таймауту). `deploy` тоді лишає новий сервер і пише `worker-failed`; повторне розгортання доводить справу.

## Тривоги, копії, відновлення (SPEC-13b, 2026-11-24)

- **Новий код тривоги без рядка в `server/src/registries/ops.ts` ламає сканер реєстру, а в роботі дає `ops/unregistered-alarm`.** Кожна хвиля додає рядок і доводить доставку `expectAlarmInTestChannel`; перед першим твердженням свого виду очистити скриньку, інакше в перевірку потрапить чужий рядок.
- **Доставка тривог — «щонайменше один раз».** Перезапуск між відправкою й позначкою дає один дубль; тести не мають вимагати рівно одного повідомлення в цьому вікні.
- **Копія з іншим ключем відмовляє ДО `pg_restore`** (`key-mismatch`): `T2F_BACKUP_KEY` після ротації зберігати, доки живуть копії, зроблені ним.
