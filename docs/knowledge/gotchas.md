# Підводні камені

Короткі записи про те, що наступна сесія інакше відкриє заново. Кожен запис: що сталося, чому, що робити. Нові — знизу свого розділу.

## Розгортання й вузол (SPEC-13a, 2026-11-18)

- **`ufw limit 22/tcp` ламає власні інструменти.** Обмеження пускає ≈6 нових з’єднань за 30 с з однієї адреси, а `infra/ops` відкриває з’єднання SSH на кожен крок і перевірку — підготовка вузла падала з `Connection timed out`. Невдалі спроби теж подовжують блокування. Правило на вузлі — `ufw allow 22/tcp` (вхід лише за ключем, root і паролі вимкнено); міняти правило брандмауера — одним з’єднанням (`allow` перед `delete limit`).
- **Крок, що вимикає вхід root, не можна перевіряти новим з’єднанням root.** Перевірка `sshd -T` іде в тому самому з’єднанні, що й зміна; ззовні підтвердження — вхід `deploy`.
- **`pnpm import …` — вбудована команда pnpm 12.** Скрипт пакета викликати як `pnpm run import catalog [--apply]` (у контейнері сервера: `docker exec <сервер> pnpm run import catalog --apply`).
- **Локальний dev-сервер переписує `server/src/payload-types.ts` з LF.** `git status` показує файл зміненим, `git diff` порожній; запобіжник «чисте дерево» в `deploy` чесно відмовляє. Ліки: `git add server/src/payload-types.ts` (вміст той самий, індекс оновлюється).
- **Перше розгортання середовища не має звідки взяти каталог по https.** Збірка сайту (`test` + `http`) читає `T2F_CATALOG_URL`; Worker’а середовища ще немає. Для першого разу: локальний сервер worktree (`pnpm stack`) і `T2F_CATALOG_URL=http://127.0.0.1:<порт>` (http на loopback дозволено лише в тестовій збірці); після `import catalog --apply` на вузлі наступні розгортання беруть каталог із самого середовища.
- **Нове ім’я в Cloudflare може «не існувати» на машині розробника ще довго** (локальний кеш негативної відповіді DNS). Перевіряти через `curl --resolve <ім’я>:443:<адреса з nslookup <ім’я> 1.1.1.1>`.
- **`next build` Payload потребує змінних середовища вже під час збірки** («Collecting page data» завантажує `payload.config.ts`). В образі це заглушки класу `test` лише в одному `RUN`; до бази збірка не під’єднується.
- **Payload не читає `migrations/index.ts`** під час `payload migrate` — лише файли міграцій у теці.
- **Compose `environment:` перекриває `ENV` образу й `env_file`.** `T2F_ENV`, `T2F_HOST`, `T2F_SERVER_PORT` задає Compose вузла; `T2F_COMMIT` вшито в образ — у файли змінних їх не писати.
- **`wrangler deploy` без термінала мовчки забирає Custom Domain в іншого Worker’а** (`override_existing_origin`). Для основного домену єдині запобіжники — подвійний прапорець і перевірка власника імені (`--take-domain-from`).
- **Тести, що запускають `cf.mjs`, мусять передавати тимчасову `localDir`.** Інакше вони читають справжню `infra/cloudflare/.local` (позначка Access, токен тунелю) і поводяться по-різному на різних машинах.
- **`scripts/check-secrets.mjs` дивиться лише відстежувані файли.** Для нових файлів — спершу `git add -N`. Тестовий пароль чи ключ потребує `// check-secrets: allow <причина>` у тому ж рядку (порожня позначка не рахується).
- **Вимкнений вузол DigitalOcean тарифікується;** зміна розміру лише CPU/RAM зворотна (диск не росте), потребує вимкнення: ≈110 с простою на вузлі з 9 ГБ зайнятого диска.
- **Завантаження статики Worker’а інколи обривається** («Asset upload failed. Retrying…» до таймауту). `deploy` тоді лишає новий сервер і пише `worker-failed`; повторне розгортання доводить справу.

## Тривоги, копії, відновлення (SPEC-13b, 2026-11-24)

- **Новий код тривоги без рядка в `server/src/registries/ops.ts` ламає сканер реєстру, а в роботі дає `ops/unregistered-alarm`.** Кожна хвиля додає рядок і доводить доставку `expectAlarmInTestChannel`; перед першим твердженням свого виду очистити скриньку, інакше в перевірку потрапить чужий рядок.
- **Доставка тривог — «щонайменше один раз».** Перезапуск між відправкою й позначкою дає один дубль; тести не мають вимагати рівно одного повідомлення в цьому вікні.
- **Копія з іншим ключем відмовляє ДО `pg_restore`** (`key-mismatch`): `T2F_BACKUP_KEY` після ротації зберігати, доки живуть копії, зроблені ним.

## Вхід і листи (SPEC-10, 2026-11-25)

- **Better Auth ковтає помилку відправника коду** (`runInBackgroundOrAwait`): запит відповідає 200, хоч лист не пішов. Недоставку визначати самим: немає результату пошти після кроку BA → видалити рядок коду, звільнити паузу, відповісти `unavailable`.
- **Next збирає модулі кілька разів.** `AsyncLocalStorage` у модулі, який викликає Better Auth із синглтона `globalThis`, у іншій копії порожній; тримати його на `globalThis[Symbol.for(...)]`. Інтеграційні тести (один граф модулів) цього не ловлять — перевіряти на `stack.mjs serve`.
- **Better Auth відкидає не-IP у `x-forwarded-for` і маскує IPv6 до /64.** Власний ключ відбитка передавати як `fd00::/8` + 120 біт sha256 і ставити `advanced.ipAddress.ipv6Subnet: 128`.
- **Мертва cookie сесії на `/sign-in/*` лишається в браузері** (відповідь `Max-Age=0` губиться, якщо отриману сесію відкинули): після `getSession` → null прибирати cookie із запиту, що пересилається.
- **`T2F_AUTH_SECRET` у `.env.local` перегенеровується при кожному `db.mjs env`** і анулює всі сесії; у rehearsal/production без нього сервер не стартує, а `T2F_GOOGLE_DISCOVERY_URL` поза класом test має бути `https:` — тестові фікстури rehearsal підставляють `https://oidc.invalid/...`.
- **Тест без `T2F_EDGE_SECRET` ділить одну адресу на всіх** (`noaddr:<день>`): вбудовані ліміти Better Auth (3 за 10 с) б’ють між тестами; ставити секрет і свіжий `x-t2f-client` на абонента.
- **Тайм-аут відправлення в пошті рахується разом із чергою пулу.** При сплеску вище швидкості пулу (8/с) листи, що чекали в черзі понад 4 с, вважаються збоєм основного → запасний і запобіжник на 5 хв, а частина адрес отримує дубль від обох. Чергу не плутати зі збоєм постачальника (F1, в роботі).
- **Будь-який виклик Better Auth із завдань** (стирання, прибирання гостей) — у `runInAuthScope(deps, …)`, інакше хуки (події сесії, перенесення гостя) не бачать залежностей.
- **Compose `fake-smtp` змонтовує `./fakes/smtp` того worktree, звідки його запущено** — після злиття перезапустити з master.

## Права й профіль (SPEC-11, 2026-11-26)

- **Better Auth 1.7.28: вето `user.delete.before` повертається тихо** — без `FAILED_TO_DELETE_USER`. Щоб знати, чи гостя видалено, після `deleteUser` перечитати рядок користувача (`maybeRemoveGuest`); на виняток не покладатися. Саме `deleteUser` — одна транзакція (виняток посередині відкочує сесії, акаунти й користувача).
- **З `disableDeleteAnonymousUser: true` гість і його рядок сесії лишаються після входу**, `onLinkAccount` усе одно спрацьовує один раз, а хука `signed-out` немає. `linkGuest` сам викликає `deleteUserSessions(guestId)`, гостя прибирає лише `maybeRemoveGuest` (усі рядки злиття виконано) або `auth-guest-prune`.
- **У маршрутах `rightsOf(ctx.deps)` — не той самий об’єкт, що `rightsOf(h.deps)` у тесті:** диспетчер віддає `Object.create(deps)`, тож WeakMap дає окремі сервіси. Підміна сервісу в тесті до маршруту не доходить; збій у БД вносити обмеженим тригером (`pg_sleep`, `RAISE`), а двері-«зламати обробник» озброювати на `DoorTools.deps` (deps композиції), не на копії.
- **Програш гонки приєднання Google — не `unable_to_link_account`, а 5xx:** вставка Better Auth падає на `user_accounts_provider_account_uq`. `finishGoogleLink` мапить це на 302 `returnPath?error=google-taken`; без нього людина бачить помилку сервера.
- **`/unlink-account` Better Auth не знає нашого «останнього способу входу»**: `canUnlink`/`last-method` — власне правило (`findAccounts` + `deleteAccount`). Для акаунта з верифікованою поштою Google не останній спосіб (пошта теж спосіб); `last-method` досяжна для акаунта, створеного входом через Google з НОВОЮ адресою і `email_verified:false` (SPEC-10: пошта не підтверджена, Google — єдиний спосіб). Набір робить такий акаунт через фейковий OIDC (`googleOnlyAccount` у `tests/contract/profile.http.test.ts`; на sim — `emailUnverified`).
- **Значення Redis із добовими позначками під тестовим годинником:** годинник тесту рухається, а Redis нічого не спливає, тож у значення кладемо власний момент (`<ms>|<fp>`) і ігноруємо значення іншої доби UTC; ключ `ban:sfp:<суб’єкт>:<fp>` потрібен, щоб бан читався з БД лише при першій появі пари за добу, а не на кожен запит. Позначаються лише відбитки `fp:` (не кошик `noaddr:`).
- **Тест, що рухає спільний годинник, мусить повернути його на реальний час у `afterAll`** (`/api/_test/clock`), інакше наступний файл бачить зсунуті сезони й мітки.
- **`migrate:create` у цьому устаткуванні просить `--force-accept-warning`** (порожня міграція); `migrate:down` відкочує весь пакет (на свіжій базі — усі міграції), а не останню. DDL із частковими унікальними індексами — вручну через `sql.raw`; інваріант «один активний пас» тримає індекс, а програш гонки — `23505` (унікальність) / `23514` (check).
- **Збій приєднання паса не губиться:** `finishSignIn` пише рядок `auth_link_retries`, його повторює `auth-link-retry` (щогодини, оренда `ops-auth-link`); рядки беруться `UPDATE … WHERE id IN (… FOR UPDATE SKIP LOCKED)` і ховаються на 10 хв, а не тримаються блокуванням. Тривога `auth/link-retry` після 24 спроб тротлиться 60 с на вид: слідом за іншою такою ж тривогою рядок `log_alarms` не з’явиться, хоч у stdout вона є.
- **Новий домен тривог ламає `ops-registry.test`:** `bans/fast-store-down` лежить у рядку домену `auth`, окремий домен `bans` потребує правки тесту й реєстру.
- **Профільні помилки вводу — `validation` + `reason:'invalid-input'`:** коду `invalid-input` в `ApiErrorCode` немає. Нік-перевірка успішно повертає `null`.
- **Ключ ніку — NFKC + trim + згортання пробілів + нижній регістр** (`nickKey`); зберігається показаний вигляд (`nickDisplay`) окремо. Порівнювати лише за ключем.
- **Зміна пошти — власний потік:** значення `auth_verifications` має форму `<email>:<sha256>:<спроб лишилось>:<sentAt>` (НЕ JSON), ідентифікатор `t2f-change-email-<id>`; перевірка спершу споживає рядок, хибний код записує його назад зі спробою менше. Рядок читають `profiles.extras()` і обробник даних `profile` — міняти формат лише разом із `decodeEmailChange`.
- **zod не повинен потрапити в збірку сайту через http-адаптери:** адаптери розбирають відповіді охоронцями `authGuard`/`profileGuard` (чисті TS), без `contracts/schemas` у `lib/api/http`.
- **Поточний ключ сезону береться з `T2F_SEASON_END`** (`seasonKeyOfEnd`), не з `CatalogStore.read()`: читання каталогу надто важке для кожного `get-session` (NFR-1).
- **У Windows-середовищі `tsc --noEmit` усього репозиторію перевищує 120 с** — запускати один раз у повному прогоні, а в фазах міряти цільовими перевірками.

## Паспорт і присутність (SPEC-14, 2026-11-27)

- **`fast-store-restart` спрацьовує й тоді, коли справжній Redis працює менше ~6 хв** (uptime < момент семпла − (m − 5 хв)): після перезапуску Docker очікування здоров’я в `presence-signs`/`presence-doors` падають, доки Redis не пропрацює понад 7 хв. Ексклюзивний тест перезапуску сам чекає uptime ≥ 420 с (хук до 600 с).
- **Серверу класу `test` (serve, night-run, e2e, exclusive) семплер працює щоп’ять секунд реального часу** на `now` годинника сервера; при замороженому годиннику семпли збігаються в одну мить (upsert додає лічильники), тож вікна читаються як `sample-gap`. У процесних сьютах семплера немає. Рядок моментів `presence-finalise` у `test` теж пише записи вікон і піднімає сторінкові тривоги.
- **`presenceOf(deps)` ключується по КОРЕНЮ deps** (обхід прототипів): диспетчер тесту віддає маршрутам `Object.create(deps)`, але семплер і двері мусять брати `presenceOf(baseDeps)` — другий приймач beat-ів не створювати. Підмінювати каталог у тесті через `deps.catalogStore` / `deps.live.events` і `presenceOf(deps).clear()` (кеш каталогу 30 с).
- **Для AC-12 «скидання Redis» — `deleteByPrefix('pr:')` слота, не FLUSHDB:** FLUSHDB зніс би і ключі auth. Лічильники після скидання читаються як 0; перезапуск Redis виявляється лише за run id у семплах.
- **Збій БД + живий Redis: маркер присутності видаляється і відповідь `unavailable`** (AC-3 важить більше за формулювання AC-7). Маркер свіжий, а рядка немає — це скидання Redis, не помилка.
- **`pg` повертає `bigint` рядком:** усі часи присутності — мс у `bigint` (типи портів `PgBigint = string`); порівнювати через `Number()` лише після перевірки діапазону.
- **Диспетчер підтримує параметричні маршрути** (`:name`, один непорожній сегмент, URI-decode, `ctx.params`); точні рядки мають пріоритет. Раніше був лише точний збіг.
- **Двері `presence/fault` {fastStore:'restart'}** не перезапускають справжній Redis: вони лише міняють run id у `info()` (`<runId>~restart-<n>`) до `reset`. Справжній перезапуск — тільки в ексклюзивному тесті під замком.
- **Помилки на биті — рівномірний розподіл** (дифузія помилки, `nextBeatFails()`): 0.02 × 50 beat-ів = рівно 1 збій; акумулятор скидається при зміні частки.
- **Клієнтська присутність (`trackSurfaceLocally`) спільна для sim і http;** цикл beat-ів у http-адаптері рухається тіками `PresenceClock.subscribe`, без таймерів. Claimer видаляє штамп лише при `forbidden`+`no-presence`; інші нерозв’язні відповіді → `settled: true`.
- **Контрактний прогін паспорта на http:** жодні двері не пишуть здоровий запис напряму, тож `markHealthy` крутить двері годинника й `presence/tick` кожні 5 с (≈70 ітерацій, тайм-аут 180 с); `granted` через subscribe — лише sim (http-прогін без realtime).
- **k6-прогін проти `stack.mjs serve` (next dev) насичує сервер** (200 beat/с → ~75/с, p95 5,4 с; 100 claim/с → p95 10 с); NFR-1/2 міряти на production-збірці (`stack.mjs start` після `next build`). Прогін лишає гостей, докази й штампи `evt_london_2027` у dev-БД слота. Гостьовий ліміт створення (60/10 хв) раннер обходить очищенням `*rl:auth-guest-create*` у БД Redis слота.
- **Центрифуго:** вхід анулює відкриті з’єднання акаунта, тож живий підписник не бачить `snapshot` після злиття; AC-46 перевіряти по історії каналу (шлях відновлення).
- **Злитий гість лишає свій `author_ids`:** рядок не переноситься на акаунт (PK — суб’єкт, id унікальний), старі повідомлення вказують на суб’єкта-гостя, чий шлях після злиття порожній.
- **Гість зі штампами не прибирається** `auth-guest-prune` (`holdsOtherData`); `author_ids` покрито стиранням суб’єкта разом із `stamps`.
- **`log`-тривоги не йдуть у Telegram** (SPEC-13b AC-12): реєстровий рядок `presence/fast-store-down` у каналі перевіряти сторінковим підйомом такого ж виду. Коди raise — рядкові літерали (ops-registry-scan).
